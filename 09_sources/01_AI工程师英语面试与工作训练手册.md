# 使用说明：这不是通用英语书，而是你的面试素材库

这套材料按你的简历定制，目标岗位包括 AI Engineer、LLM Engineer、Agent Engineer、Applied AI Engineer、Multimodal AI Engineer，以及兼具后端与安全背景的 Senior Software Engineer。

- 第一轮：只练“能说出来”。先朗读，再遮住英文复述，最后尝试脱稿表达。

- 第二轮：练“能回答追问”。每个项目准备技术选择、失败路径、评估方式、成本与权衡。

- 第三轮：练“自然交流”。在会议、代码评审、排障同步中用短句表达，不追求复杂句。

- 不要背成逐字稿。记住结构与关键词，根据面试官追问调整细节。

真实性提醒：以下英文答案只使用你简历中支持的信息和通用技术推理。遇到数据规模、性能提升、团队人数、模型指标、本人贡献边界等未在简历中写明的细节，请替换成真实情况，不要编造。你的简历同时出现 Faiss 与 Milvus；面试前应确认它们分别对应哪个系统或阶段，避免把不同实现误说成同一个架构。

### 这个项目的深挖题

### **Why did you use a graph-based workflow instead of a single prompt?**

> A single prompt is useful for simple interactions, but this task involves multiple tools, intermediate artifacts, conditional branches, and possible retries. A graph-based workflow makes the state transitions explicit, gives us better control over tool execution, and makes interruption and recovery easier to manage.
>
> 中文要点：多工具、多中间结果、条件分支、重试和恢复使显式工作流更适合。
>
> *表达重点：避免说 graph 一定优于所有方案；应结合任务复杂度。*

### **How do you handle a tool failure?**

> I would validate the input before calling the tool, apply a timeout, classify the error, and retry only when the failure is transient and the operation is safe to retry. For non-recoverable errors, I would record the failure, preserve the workflow state, and either ask the user for input or route the task to a fallback path.
>
> 中文要点：输入校验、超时、错误分类、有限重试、保存状态、用户补充或降级路径。
>
> *表达重点：如果实际实现未包括某项，面试时应说 “I would design...” 而不是 “I implemented...”。*

### **How do you protect an agent from prompt injection?**

> I treat retrieved content and tool outputs as untrusted input. The agent should not let those inputs override system-level instructions. I would use least-privilege tool permissions, structured input validation, explicit action policies, output checks, and human approval for sensitive operations. I would also test the system with adversarial examples and monitor suspicious tool-call patterns.
>
> 中文要点：将检索内容和工具输出视为不可信输入；通过最小权限、结构化校验、动作策略、输出检查和敏感操作审批形成纵深防护。
>
> *表达重点：不能只回答 “I use a stronger system prompt”。*

### **How would you evaluate the music agent?**

> I would evaluate the workflow at several levels: task completion rate, tool-call success rate, failure recovery, end-to-end latency, and user satisfaction. For the generated music, I would separately assess audio quality, musical coherence, similarity to the intended reference, voice identity preservation where relevant, and content or rights compliance. I would combine automated checks with human evaluation.
>
> 中文要点：系统级指标和生成内容质量指标分开；自动指标与人工评测结合。
>
> *表达重点：量化指标要对应真实评测方案，不要臆造。*

### **Can you walk me through a typical RAG pipeline?**

> First, we parse and normalize the documents, then split them into chunks and attach useful metadata. We generate embeddings and index the chunks. At query time, we may combine vector search with keyword retrieval, merge the candidates, and rerank them with a semantic model. Finally, we pass the most relevant evidence to the LLM and ask it to answer within that context. We also need evaluation, access control, and monitoring around the pipeline.
>
> 中文要点：文档解析和标准化 → 切分与元数据 → embedding 和索引 → 向量/关键词混合检索 → 候选合并与重排序 → 基于证据生成；还要评估、权限控制和监控。
>
> *表达重点：记住按流程讲，随后再深入某一环节。*

### **How do you choose chunk size?**

> I would start from the document structure and the retrieval task rather than choosing a fixed size blindly. Chunks need enough context to preserve meaning, but they should not be so large that relevant passages become hard to retrieve. I would compare several chunking strategies on a representative evaluation set and measure retrieval and answer quality, latency, and token cost.
>
> 中文要点：根据文档结构和检索任务选切分策略；通过代表性评测集比较检索、回答质量、延迟和 token 成本。

### **How do you evaluate a RAG system?**

> I separate retrieval evaluation from answer evaluation. For retrieval, I can measure recall at k, precision at k, MRR, or nDCG when relevance labels are available. For answers, I look at correctness, groundedness, completeness, citation quality, refusal behavior, latency, and cost. I would keep a curated test set and compare every major change against a baseline.
>

# 04 · Agent / RAG / 模型工程技术问答

## Agent 与工具调用

### **What is the difference between a workflow and an autonomous agent?**

> A workflow follows a defined sequence or graph of steps, while an agent can use model-driven decisions to choose actions based on context. In practice, I prefer explicit workflows for high-risk or predictable operations, and allow more agentic behavior where flexibility is valuable. Many production systems combine both.
>
> 中文要点：确定性工作流更容易控制；Agent 可根据上下文选择动作；生产系统常结合两者。

### **How do you design reliable tool calling?**

> I define typed input and output schemas, validate arguments, apply timeouts, and classify errors. I use bounded retries only for transient failures, make non-idempotent operations safe where possible, and log tool calls with correlation IDs. The workflow should know whether to retry, ask the user, use a fallback, or stop safely.
>
> 中文要点：Schema、参数校验、超时、错误分类、有限重试、幂等性、关联 ID 和明确失败路径。

### **How do you manage long-running tasks?**

> I separate the user request from the execution state. The workflow should persist progress, expose meaningful status updates, and support resumption after transient failures. For long-running generation, I would also consider job queues, cancellation, resource limits, and cleanup of intermediate artifacts.
>
> 中文要点：持久化状态、进度更新、续跑、队列、取消、资源限制和中间产物清理。

### **How do you control agent cost and latency?**

> I track token usage, tool latency, model latency, retries, and end-to-end completion time. I can route simple tasks to smaller models, parallelize independent operations, cache safe repeated results, limit unnecessary tool calls, and set budgets or stopping conditions. I would validate the impact against task quality.
>
> 中文要点：监控 token、工具和模型延迟、重试、端到端时长；小模型路由、并行、缓存和调用预算，前提是质量可接受。

### **What should an agent log?**

> I would log the request or trace ID, workflow state transitions, tool name, validated arguments where safe, duration, status, retry count, and structured error information. I would avoid logging secrets or sensitive user content unnecessarily, and define retention and access policies.
>
> 中文要点：记录 trace ID、状态转移、工具名、安全范围内的参数、时长、结果、重试和错误；避免泄露秘密或敏感内容。

## LLM 微调与推理部署

### **When would you choose RAG over fine-tuning?**

> I use RAG when the model needs access to changing or private knowledge and the source should be traceable. Fine-tuning is more suitable when I need to adapt style, task behavior, or domain-specific patterns that are difficult to express through prompting alone. They are not mutually exclusive; a system may use both. I would decide based on freshness, data governance, evaluation results, and operating cost.
>
> 中文要点：RAG 适合动态/私有且需要可追溯的知识；微调适合任务行为、风格与模式适配；两者可结合。

### **How would you decide whether to use LoRA?**

> I would consider LoRA when full fine-tuning is too expensive or when I need parameter-efficient adaptation. Before training, I would define a representative dataset, a held-out evaluation set, and a baseline. I would compare task quality, regression risk, memory use, inference latency, and maintenance cost.
>
> 中文要点：LoRA 是参数高效方案之一；需先定义数据、留出集和基线，再比较质量、回归风险、显存、延迟和维护成本。

### **What do you know about vLLM?**

> vLLM is an inference-serving framework designed to improve LLM serving efficiency. In evaluating an inference stack, I look at throughput, time to first token, inter-token latency, GPU memory use, batching behavior, concurrency, and operational stability. The right configuration depends on model size, context length, traffic pattern, and hardware.
>
> 中文要点：不要只说“加速推理”；需关注吞吐、首 token 延迟、token 间延迟、显存、批处理、并发与稳定性。

### **How do you deploy an AI model as a service?**

> I separate model loading from request handling, define a stable API contract, validate inputs, set timeouts and resource limits, and expose health checks and metrics. I also plan model versioning, rollout and rollback, concurrency control, queueing for expensive tasks, and load testing before production.
>
> 中文要点：API 契约、输入校验、超时、资源限制、健康检查、指标、版本、灰度/回滚、并发与压测。

### **How would you evaluate a fine-tuned model?**

> I would compare it with the base model on a held-out dataset that reflects real usage. I would measure task-specific quality, robustness, safety, and regressions on general capabilities. I would also inspect representative failures rather than relying only on a single aggregate score.
>
> 中文要点：在贴近真实使用的留出集上与基座对比；评估任务质量、鲁棒性、安全和能力回退，并分析失败案例。

## 音乐多模态与歌声转换

### **How would you build cross-modal music search?**

> I would first define the supported query types, such as text descriptions, humming, mood, or reference audio. I would encode the query and candidate tracks into compatible embedding spaces, retrieve candidates efficiently, and then rerank them using task-specific signals. I would evaluate retrieval quality across query types because humming and text descriptions have different failure modes.
>
> 中文要点：明确文本、哼唱、情绪或参考音频等查询类型；跨模态 embedding 召回，再重排；按查询类型分别评估。

### **How do you evaluate a cover-generation or voice-conversion system?**

> I would separate content preservation from voice similarity and audio quality. Depending on the task, I would assess lyric or melody preservation, speaker or timbre similarity, artifacts, musicality, timing, and listener preference. Automated metrics can help with regression checks, but perceptual quality should also be evaluated by human listeners.
>
> 中文要点：分开评价内容保真、音色相似、音频质量、瑕疵、音乐性、节奏和听众偏好。

### **What are the main engineering challenges in audio-generation pipelines?**

> The challenges include long-running GPU jobs, large intermediate files, model-specific dependencies, concurrency and queue management, reproducibility, and consistent audio post-processing. I would use job states, artifact tracking, timeouts, resource quotas, and clear error reporting to make the pipeline easier to operate.
>
> 中文要点：GPU 长任务、大中间文件、依赖、并发与队列、复现、后处理一致性；通过任务状态、产物追踪、超时和资源配额治理。

### **How do you handle copyright and safety in a music agent?**

> I would treat rights and safety checks as part of the workflow rather than a final optional step. Depending on the product policy, checks could include source authorization, user rights declarations, reference-content restrictions, provenance records, and blocking or review rules for high-risk cases. The exact policy should be agreed with legal and product teams.
>
> 中文要点：将版权与安全作为工作流中的步骤；具体依赖产品政策，并与法务/产品共同确认。

## Incident response · 故障排查

| **English**                                                        | **中文**                               |
|--------------------------------------------------------------------|----------------------------------------|

# 08 · 高频短语、句型与连接表达

## 高价值句型框架

| **句型**                         | **含义**               | **简历相关示例**                                                            |
|----------------------------------|------------------------|-----------------------------------------------------------------------------|
| I’m responsible for…             | 我负责……               | I’m responsible for model serving and workflow orchestration.               |
| I worked on…                     | 我参与/负责过……        | I worked on an LLM-assisted security triage system.                         |
| I led the development of…        | 我主导开发了……         | I led the development of a WAF rule scheduling module. (仅在真实主导时使用) |
| I contributed to…                | 我参与贡献了……         | I contributed to the retrieval pipeline and evaluation.                     |
| The main challenge was…          | 主要挑战是……           | The main challenge was handling long-running tool calls.                    |
| We chose X because…              | 我们选择 X 是因为……    | We chose hybrid search because exact technical terms mattered.              |
| The trade-off is…                | 需要权衡的是……         | The trade-off is better recall versus higher latency.                       |
| I validated this by…             | 我通过……验证了这一点   | I validated this by comparing retrieval metrics on a held-out set.          |
| The root cause turned out to be… | 根因最终是……           | The root cause turned out to be a connection pool limit.                    |
| To avoid this, I…                | 为了避免这个问题，我…… | To avoid this, I added input validation and a regression test.              |
| From an operational perspective… | 从运维角度看……         | From an operational perspective, we need tracing and rollback.              |
| One limitation is…               | 一个局限是……           | One limitation is that automatic metrics may not capture musicality.        |
| A safer approach would be to…    | 更稳妥的办法是……       | A safer approach would be to require human approval for risky actions.      |
| Based on the evidence…           | 基于现有证据……         | Based on the evidence, the bottleneck is in retrieval.                      |
| I would start by… and then…      | 我会先……，然后……       | I would start by profiling the service and then optimize the bottleneck.    |

## 组织回答的连接词

| **表达**                    | **含义**           | **示例**                                                                                      |
|-----------------------------|--------------------|-----------------------------------------------------------------------------------------------|
| First / Then / Finally      | 首先 / 然后 / 最后 | First, I validate the request. Then, I retrieve the evidence. Finally, I generate the answer. |
| Because / Therefore         | 因为 / 因此        | The query was expensive. Therefore, we added an index.                                        |
| However / On the other hand | 然而 / 另一方面    | Caching reduces latency. However, it adds invalidation complexity.                            |
| For example / Specifically  | 例如 / 具体来说    | We used several guardrails. Specifically, we validated tool arguments.                        |
| As a result                 | 因此，结果是       | As a result, the workflow became easier to debug.                                             |
| In practice                 | 实际中             | In practice, we also need to handle timeouts and retries.                                     |
| From my experience          | 根据我的经验       | From my experience, retrieval quality is often the bottleneck.                                |
| To be precise               | 准确地说           | To be precise, the metric measures answer correctness on our test set.                        |
| That said                   | 话虽如此           | That said, the simplest solution may be sufficient at this scale.                             |
| Overall                     | 总体而言           | Overall, the approach improves control but adds operational work.                             |

# 09 · 14 天强化计划与自测标准

| **天数** | **主题**     | **任务**                                                 | **验收标准**                             |
|----------|--------------|----------------------------------------------------------|------------------------------------------|
| Day 1    | 自我介绍     | 朗读 30 秒、60 秒版本各 5 次；录音 1 次。                | 脱稿讲 45–60 秒。                        |
| Day 2    | 职业故事     | 按“安全→后端→AI→Agent”讲职业路径 3 次。                  | 不看稿讲 90 秒。                         |
| Day 3    | 音乐 Agent   | 练 Project A；回答 Why graph workflow? 和 tool failure。 | 连续讲 2 分钟并回答 2 个追问。           |
| Day 4    | RAG          | 练 RAG pipeline、chunk size、hybrid search、evaluation。 | 画出流水线并用英语解释。                 |
| Day 5    | 安全研判     | 练 alert noise、rule + LLM、false positives。            | 回答 3 个题，每题 60–90 秒。             |
| Day 6    | 模型服务     | 练 LoRA、vLLM、latency、throughput、deployment。         | 解释一个模型服务架构。                   |
| Day 7    | 行为面试     | 写 3 个真实 STAR 故事。                                  | 每个故事 90–150 秒。                     |
| Day 8    | 站会与 PR    | 练进度汇报、提出评审建议、回应评论。                     | 即兴完成 5 轮角色扮演。                  |
| Day 9    | 故障排查     | 讲现象、排查步骤、根因、缓解、预防。                     | 做一段 90 秒 incident update。           |
| Day 10   | 系统设计     | 练 RAG 服务架构、扩展性和故障模式。                      | 讲 5 分钟系统设计。                      |
| Day 11   | 不确定性表达 | 练澄清、承认不确定、验证假设。                           | 不使用“我不知道”结束回答，补上验证方法。 |
| Day 12   | 技术深挖     | 随机抽 8 道技术题，先讲框架再补细节。                    | 每题结构清晰，避免超长句。               |
| Day 13   | 完整模拟     | 完成自我介绍、项目、技术问答和行为题。                   | 模拟 25–30 分钟。                        |
| Day 14   | 复盘强化     | 回听录音，挑 10 个最卡的表达，重复改写。                 | 重录自我介绍与核心项目故事。             |

## 面试前 24 小时检查清单

- 能脱稿完成 60 秒和 2 分钟自我介绍。

- 每个核心项目都能说清：目标、本人贡献、架构、难点、指标、权衡、失败处理。

- 对简历上的 85%+ 准确率、7 项专利、模型/框架名称和时间线准备了真实解释。

- 确认 Faiss 与 Milvus 分别出现在哪个项目或实现阶段。

- 每个技术答案至少讲出一个 trade-off，而不只罗列技术名词。

- 准备 3 个想问面试官的问题：团队当前挑战、上线流程、成功标准。

- 把“我做过”“我参与过”“我会考虑”区分清楚，不夸大个人实际经历。
